# BufRom — A weather journal for Romagna

**English** | [Italiano](README.it.md)

BufRom is a small **C++20 application linked directly to libwreport**.
It downloads temperatures in BUFR format from MeteoHub, stores them in SQLite,
and generates HTML, CSV, and SVG charts with gnuplot. Apache serves the static
files.

**Public website: [BufRom — Diario meteo della Romagna](https://www.molara.net/bufrom/).**
Version 0.2.0-dev, tested on Debian 13: BUFR acquisition, the archive, and
publication on quixote are working. The HTTPS page, SVG charts, CSV, and previous
release have been checked externally. Idempotent reimporting and preservation of
the published site after a failed download have also been verified on the server.
The systemd timer is active: a first automatic update succeeded using an
accelerated test; the normal schedule is hourly. Subsequent hourly runs remain
to be observed.
The repository is <https://github.com/fmolara/bufrom>.

The domain's HTTPS VirtualHost is configured independently of WordPress;
its restoration was checked externally, including the release generated by the timer.

## Building and testing on Debian

This section is for the **development machine**. For a server running an already
compiled binary, follow
[Production installation without compiling](#production-installation-on-debian-without-compiling).

Dependencies to install as administrator (sudo is unnecessary if the
administrator logs in directly as root):

```sh
apt install build-essential pkg-config libwreport-dev wreport-common \
    libsqlite3-dev libssl-dev gnuplot-nox curl jq util-linux coreutils
```

As a regular user, from the project directory:

```sh
make -j2
make check
./build/bufrom --help
```

GCC 13 or later with `std::format` is required; the project retains its Makefile
and C++20. The only additional libraries are SQLite and OpenSSL (SHA-256).
Acquisition uses Bash, curl, and jq: decoding and interpretation remain in the
C++ core. Pipeline tests use Python 3 to check HTML/CSV; `make check` runs offline
and requires no account, network connection, Apache, or special privileges.
The service does not use Python.

The suite retains the prototype's seven native test groups and integration test,
adds a real 648-byte MeteoHub fixture, and checks identities across networks,
timestamps, levels, units, missing values, persistence, duplicates, corrections,
conflicts, and SQLite rollback. A pipeline test using temporary synthetic inputs
also checks download/gnuplot failures, versioned assets, and release restoration.
Live tests are separate: recorded details and versions are in
[VALIDATION-debian.txt](VALIDATION-debian.txt), in Italian.

## Production installation on Debian without compiling

The server only needs an already compiled executable and its runtime dependencies.
The binary must be built for the same architecture and a Debian version compatible
with the server: the one tested in development targets **Debian 13 (trixie), amd64**.
For Debian 12 or other architectures, a suitable binary must be prepared on the
development machine.

A development binary package for Debian 13 amd64 is available in the
[v0.2.0-dev prerelease](https://github.com/fmolara/bufrom/releases/tag/v0.2.0-dev).
Manual execution and the first accelerated automatic run have been verified in
production. Download:

- `bufrom-0.2.0-dev-debian13-amd64.tar.gz`: executable, tables, scripts, and examples;
- `bufrom-0.2.0-dev-source.tar.gz`: corresponding source code and its licenses;
- `SHA256SUMS`: archive checksums.

The package contains a `bufrom-0.2.0-dev-COMMIT` directory and a `BUILD-INFO.txt`
file recording the commit, architecture, and library versions. It is not a `.deb`
and contains no operational database, acquired raw data, logs, or private
configuration. GitHub's automatic source-only archives do not include the executable.

To prepare new archives on the development machine, from a clean checkout:

```sh
./scripts/package-runtime.sh ../bufrom-release
```

The script builds and tests the project in development, then produces the binary,
source archive, and checksums in a directory outside the repository.
Running BufRom in production requires no compiler, `make`, `pkg-config`, `-dev`
packages, Python, or Git.

On **Debian 13**, the administrator installs the runtime dependencies as root:

```sh
apt install --no-install-recommends \
    libwreport3t64 wreport-common libsqlite3-0 libssl3t64 libstdc++6 \
    gnuplot-nox fonts-liberation curl jq bash util-linux coreutils findutils \
    ca-certificates tar gzip
```

**In production, use `libwreport3t64`, without `libwreport-dev`, `libsqlite3-dev`,
or `libssl-dev`.** The command in “Building and testing” is for the development
machine. In particular, `libwreport-dev` depends on `liblua5.1-0-dev`, which
recommends Libtool; further recommendations and dependencies may also install
Automake and Autoconf. These tools are unnecessary for running BufRom.

`--no-install-recommends` retains mandatory dependencies while avoiding, among
other things, the chain of programs recommended by gnuplot through `groff`, such
as Ghostscript and ImageMagick, which the journal's SVG charts do not need.
`fonts-liberation` is installed explicitly to provide fonts.

APT resolves the other required libraries. Apache must already be configured to
serve the chosen public directory; the application runs separately from the web
server. The `sqlite3` command-line tool is optional for maintenance and backups.

As the service user, verify the supplied checksum and install the archive in a
new directory outside the document root. For example:

```sh
BUFROM_DIR="$HOME/.local/opt/bufrom-0.2.0-dev"
mkdir -p "$HOME/.local/opt"
mkdir "$BUFROM_DIR"
tar -xzf /path/to/bufrom-0.2.0-dev-debian13-amd64.tar.gz \
    --strip-components=1 -C "$BUFROM_DIR"
"$BUFROM_DIR/build/bufrom" --version
ldd "$BUFROM_DIR/build/bufrom"
install -d -m 700 "$HOME/.config/bufrom"
install -m 600 "$BUFROM_DIR/config/bufrom.conf.example" \
    "$HOME/.config/bufrom/bufrom.conf"
```

`ldd` must resolve every library, with no `not found` lines. Keep the archive's
directory structure: `build/bufrom` locates its tables in `../tables` relative to
the executable's directory, and the scripts call other files in the package.
Adapt the private configuration: set `PROGRAM` to the absolute path of
`build/bufrom`, `STATE_DIR` to a private directory outside the package and the
document root, and `PUBLIC_DIR` to the dedicated directory served by Apache.
The examples use paths for the `wreport` service account; adapt them for a
different layout or an installation in the user's home directory.

Once configured, run the first update as the service user:

```sh
"$BUFROM_DIR/scripts/update.sh" "$HOME/.config/bufrom/bufrom.conf"
```

Then check the page through its HTTPS URL. To enable the timer, see
[OPERATIONS.md](OPERATIONS.md#pianificazione), in Italian, adapting the user,
paths, and unit configuration to the installed package. For subsequent upgrades,
install a new compatible archive in a new directory and follow the operational
procedure; the database and raw files remain in the same `STATE_DIR`.
Binary installation and the first update have been verified on quixote; the timer
has been enabled and its first accelerated automatic run succeeded.
The quixote server uses a dedicated `wreport` service account:
[creation, paths, and permissions](OPERATIONS.md#utente-di-servizio-wreport), in Italian.
The configuration and systemd unit examples are prepared for this account.

## From BUFR to the journal

1. `scripts/fetch-meteohub.sh` uses the official public map endpoint with bounded
   area, network, and UTC interval. It checks HTTP status, response type, the BUFR
   magic bytes, and complete native decoding; it saves a receipt with the query,
   hash, and acquisition time.
2. `src/bufr.cpp` uses `BufrBulletin::read`, `BufrCodecOptions::create`, and
   `BufrBulletin::decode`. It traverses `subsets`, `Var`, `Varinfo`, and `next_attr`.
   It rejects empty or truncated files, HTML/JSON, and extraneous bytes, including
   trailing data.
3. `src/meteohub.cpp` recognizes the observed template, preserves variable
   positions, and interprets network, coordinates, calendar, level, and time.
   It uses `isset`, `enqi`, `enqd`, `enqs`, and `convert_units`; this meteorological
   interpretation is the application's responsibility, beyond decoding alone.
4. `src/archive.cpp` preserves intact BUFR files by SHA-256 and imports them in
   a SQLite transaction. Revisions link the value, batch, and original position.
5. `src/render.cpp` reads the selected observations, invokes gnuplot without a shell
   through `posix_spawnp`, and prepares a complete directory before publication.
   `scripts/update.sh` atomically replaces the entry-point HTML file.

The application uses no external BUFR converter, JSON converted back into BUFR,
application server, or web framework.

## Data source and supported profile

Source: [MeteoHub, Agenzia ItaliaMeteo](https://meteohub.agenziaitaliameteo.it/ui/user-guide),
[surface observations](https://dati.agenziaitaliameteo.it/dataset/osservazioni-idro-meteo-stazioni-al-suolo).
Network/dataset: `simnbo` (`simnbo-emiliaromagna` in the catalogue), attributed to
**Arpae Emilia-Romagna Idro-Meteo-Clima Service**, data licensed under **CC BY 4.0**.
The license and attribution were checked through the official API:
[`datasets?licenceSpecs=true`](https://meteohub.agenziaitaliameteo.it/api/datasets?licenceSpecs=true).

| Source-provided name | Station identity (network and coordinates) | Ground elevation |
| --- | --- | --- |
| Forlì Urbana | `simnbo:44.22039,12.04182` | 51 m |
| Bertinoro | `simnbo:44.15206,12.14217` | 139 m |

The feed provides no separate numeric station code: the B01019 name is preserved;
stable identity follows DB-All.e fixed stations (network and coordinates).
No WMO codes are invented. A change in coordinates identifies a new station,
without automatically merging its history with the previous location.

The operational profile is deliberately narrow:

- BUFR edition 4, category 255, originating centre/subcentre 200/0, master table 0
  version 14, local tables version 1; a verified expanded sequence of **18 descriptors**.
- B01194 network; B04001–B04006 observation date and time in UTC, all required;
  B01019 name; B05001/B06001 coordinates; B07030 ground elevation, B07031 barometer elevation.
- B07192/B07193 = `103,2000`: a height of 2000 mm (2 m) above ground.
  Elevation above sea level remains distinct from sensor height.
- B04192–B04194 = `254,0,0`: instantaneous temperature, with no temporal aggregation.
- B12101 in K, scale 2, resolution 0.01 K; Celsius conversion through wreport.
  The native value is preserved without rounding in the archive; the HTML table
  displays two decimal places.
- Other templates or contexts are excluded with origin and reason recorded in
  the logs. Repeated descriptors are not flattened into a map. The 17-descriptor
  templates encountered on other networks are outside this profile.

The tables in `wreport-common` alone do not contain these local definitions.
[tables/](tables/PROVENANCE.txt) includes the required official DB-All.e tables,
with provenance, hashes, and license. The CLI finds them in `../tables` relative
to the executable's directory (`build/bufrom`); `WREPORT_EXTRA_TABLES` can specify
an explicit location. Neither the BUFR files nor the system tables are modified.
The program must remain together with its `tables` directory.

`src/observations.cpp` also retains the limited v0.1.0 WMO profile for manual
`build` use and historical fixtures; the operational `site` command only accepts
the MeteoHub profile described above and the simnbo network.

## Quality, missing values, series, and archive

The acquired sample contained no quality attributes. This does not certify the
measurements: no automatic validation or correction rules are applied.
Any temperature attributes are preserved with their codes and values and
marked as **uninterpreted** on the page and in CSV.

Missing values remain NULL in SQLite and empty in CSV. Series distinguish station,
profile, variable, level, temporal meaning, unit, and resolution. In the legacy
profile, unknown height keeps different provenance separate; it does not establish
homogeneity. Charts use points only, with no interpolation, aggregation, or lines
across gaps. The page reports the last successful update and each station's latest
observation, and warns when data are more than three hours old at generation time.
Dates remain visible even when the service stops updating.

SQLite schema version 1:

- `batches`: SHA-256, origin, dataset, UTC acquisition time, original BUFR file path;
- `revisions`: observation and full context, quality, hash, and positions in the BUFR;
- `current_observations`: link to the current revision of each key.

The key comprises profile, network/station, variable, UTC instant, level, and
temporal context; components are length-prefixed, avoiding collisions and SQL
NULLs in the key. The same BUFR file is not imported again, even if renamed or
presented again after a correction. An identical value from a different batch is
a duplicate. A different value from a **new batch acquired later** creates a
revision; the previous one remains traceable. Conflicting acquisitions with equal
or out-of-order timestamps, and conflicts within the same batch, fail the entire
transaction. Acquisition time does not establish a correction's authority: this is
the release's explicit policy, not a reconstruction of the source's editorial history.

The service rereads the last **30 hours**, configurable up to 216 hours within the
anonymous-access limit of the last 10 days, split by UTC day. It recovers late
arrivals and corrections only within that window; a complete replica of older
corrections is not guaranteed. Local history and BUFR files are not deleted.
A lack of new measurements does not empty the archive; a batch with no
interpretable observations stops the update and preserves the previous site.

## Running the application

Copy [config/bufrom.conf.example](config/bufrom.conf.example) to a private location
outside the repository and document root, adapt the paths, and set permissions
to `0600`. This public data profile requires no MeteoHub account.
`STATIONS` selects the two real station identities, `OVERLAP_HOURS` the interval
reread, and `DISPLAY_HOURS` the hours displayed (initially 48).

```sh
./scripts/update.sh /private/path/bufrom.conf
./scripts/rollback.sh /private/path/bufrom.conf
```

`PUBLIC_DIR` must be a dedicated empty directory or one already initialized by
BufRom; the program refuses to replace an unrelated site. It uses a `flock` lock,
a global 15-minute timeout, HTTP timeouts, and at most two retries. Database, raw
files, receipts, logs, and status remain in private `STATE_DIR` storage.
A concurrent invocation exits with status 75.

Complete releases are stored under `PUBLIC_DIR/releases/ID`. The entry-point HTML
references SVG and CSV through URLs containing the release ID; replacement of
`index.html` is atomic. Releases are retained, including the previous one.
Their `index.html` is a copy for restoring **at the site root**, not an entry point
to open within `releases/ID`. Failed generation preserves the previous public HTML.
An atomic HTML switch does not guarantee durability after a power failure.

[OPERATIONS.md](OPERATIONS.md), in Italian, describes scheduling, permissions,
logs, backups, and restoration. The systemd examples correspond to the timer
installed on quixote; the first accelerated automatic activation has been verified,
while subsequent hourly runs remain to be observed.

## Core commands

```sh
./build/bufrom inspect --details tests/data/meteohub-simnbo.bufr
./build/bufrom export --output variables.csv tests/data/meteohub-simnbo.bufr
./build/bufrom verify tests/data/*.bufr
./build/bufrom import --database /private/data/observations.sqlite \
    --raw-dir /private/data/raw --origin SOURCE_URL --dataset simnbo FILE.bufr
./build/bufrom site --database /private/data/observations.sqlite \
    --output new-directory --repository https://github.com/fmolara/bufrom
./build/bufrom build --output historical-example \
    --station 16148 --station 16149 tests/data/synop3new.bufr
```

`export` preserves positions, attributes, and undefined values, overwrites an
existing CSV, and refuses to overwrite its input. `verify` uses `encode` and
`Bulletin::diff`: a semantic check using the same library, not an independent
WMO conformance check. `build` and `site` reject an existing output directory.
`examples/site` remains the original historical example from **15 August 2010**.
